# 视觉快反优化方案

## 1. 目标

把摄像头监管从“最多等待 20 秒后才开始理解”改成更接近实时的事件响应，同时控制并发、重复提醒和误判。

本轮目标：

- 摄像头开启后约 1 秒开始第一次观察。
- 一轮完成 5 秒后再发起下一轮，不堆积并发请求。
- Vision 一次返回场景、状态和置信度，不再串行调用第二个模型分类。
- 高置信手机事件可单帧确认；离开、回来及其他状态需连续两帧确认。
- 手机、离开、回来使用固定短台词，跳过 LLM 台词生成。
- 保留现有 TTS、人设上下文、冷却策略、日志和埋点。

## 2. 新链路

```text
摄像头
  → 1 秒后首次截图
  → Vision 返回 scene + state + confidence
  → 状态稳定器
  → 发言策略
  ├─ PHONE / ABSENT / RETURN：固定快反台词 → TTS
  └─ 其他需要发言的事件：LLM 生成人设台词 → TTS
  → 本轮结束 5 秒后安排下一轮
```

相比旧链路，删除了 `Vision 描述 → DeepSeek 分类` 中的第二次分类请求。关键事件也删除了 `DeepSeek 生成台词`，因此关键路径只剩 Vision 和 TTS。

## 3. 调度策略

旧版使用固定 `setInterval(20s)`。新版使用串行 `setTimeout(5s)`：

1. 当前观察完成（成功或失败）。
2. 等待 5 秒。
3. 发起下一轮。

因此实际周期为 `本轮接口耗时 + 5 秒`，不会因为接口慢而产生请求队列。暂停、关闭摄像头、结束会话或视觉服务不可用时，不再安排下一轮。

## 4. 状态稳定规则

Vision 返回以下结构：

```json
{
  "scene": "用户低头看着手中的手机",
  "state": "PHONE",
  "confidence": 0.92,
  "phoneVisible": true
}
```

允许状态：

```text
STUDYING / READING / WRITING / COMPUTER_WORK
PHONE / RESTING / ABSENT / DRINKING / STRETCHING
OTHER / UNKNOWN
```

确认规则：

| 场景 | 确认条件 | 目的 |
| --- | --- | --- |
| `PHONE` 且置信度 ≥ 0.8 | 1 帧 | 提升手机快反速度 |
| 其他可靠状态 | 连续 2 帧 | 抑制姿态变化造成的误判 |
| `UNKNOWN` 或置信度 < 0.55 | 通常保留上一个确认状态；上一个状态为 `PHONE` 时按下方规则退出 | 避免普通状态抖动，同时防止手机状态粘住 |

`PHONE` 有额外的证据约束：只有手机本体明确可见、用户正在观看或操作，并且置信度不低于 0.75 才接受。低头、手部在画外或无法看清活动时不能判定为手机。若上一个确认状态是 `PHONE`，第一帧无法确认手机时立即停止提醒，连续两帧无法确认则退出 `PHONE`，避免旧状态无限粘住。

状态稳定数据保存在现有 `policyState` 中：

```text
confirmedState
candidateState
candidateCount
```

## 5. 快反事件与台词

关键事件不调用 LLM 生成台词：

| 事件 | 台词池 |
| --- | --- |
| `PHONE_ENTER` | “手机。” / “放下。” |
| `PHONE_REPEAT` | 不使用预设；结合上一帧行为、上一句提醒、持续时长和当前任务由 AI 临时生成 |
| `ABSENT_ENTER` | “去哪？” / “人呢？” |
| `ABSENT_RETURN` | “回来了？” / “继续。” |

严格模式下，关键事件的文字会在决策返回后立即显示，不等待 TTS 首包；手机和离开事件即使关闭普通“TA 主动语音”也仍会播放监管提醒。如果 TTS 被抑制、失败或未播放，下一视觉轮次仍会再次提醒。手机事件不再受“距上次发言”或“同一次事件”时间冷却限制。第一次手机提醒使用极短快反保证速度；后续仍为手机状态时由 AI 读取上一帧行为与上一句已说内容后临时生成，避免固定台词循环。请求仍采用串行调度，因此不会并发播放多轮提醒。

当前固定的是文字，语音通过角色 TTS 流式生成，以保证不同角色声音一致。火山引擎与 ElevenLabs 均由后端透传 24 kHz PCM 音频块，前端收到首批音频后即开始排播，不等待完整音频生成。若实测 TTS 首字节仍是主要延迟，下一步可按 `角色 voiceId + event + 文案版本` 预生成并缓存音频；缓存命中时直接播放，失败时回退到流式 TTS。

### 流式 TTS 实现

```text
TTS 服务产生 PCM 音频块
  → API 收到一块就 res.write 一块
  → 浏览器 ReadableStream 逐块读取
  → Web Audio 将 PCM 转为 AudioBuffer
  → 保留约 180ms 播放缓冲并连续排播
```

响应使用 `X-Accel-Buffering: no`，降低代理层聚合小数据块的概率。ElevenLabs 使用 `/stream?output_format=pcm_24000` 和低延迟 `eleven_flash_v2_5` 模型；可通过 `ELEVENLABS_TTS_MODEL` 环境变量覆盖模型。火山引擎继续解析 SSE 中的 Base64 PCM 数据。两条路径最终返回相同的 `pcm_s16le / 24000 Hz` 格式，因此前端不再需要等待完整 MP3 下载和解码。

## 6. 成本和延迟预期

- 观察间隔由 20 秒降为约 5 秒，Vision 调用上限约提高 4 倍。
- 删除每轮 DeepSeek 状态分类请求，可抵消一部分请求量和延迟。
- 手机高置信事件通常在下一帧直接确认；平均发现等待约为半个观察周期，加上 Vision 耗时。
- 离开和恢复需要两帧，因此响应更慢，但误报风险更低。
- 快反事件不等待 LLM 文案生成；最终开口延迟主要由 Vision 与 TTS 决定。

## 7. 验收指标

内测重点观察：

1. 从拿起手机到 `PHONE_ENTER` 决策的 P50/P95 时间。
2. Vision 请求 P50/P95、失败率和每小时调用量。
3. `rawState`、`confidence` 与最终 `state` 的差异。
4. `candidateState` 被取消的次数，用于判断模型抖动。
5. 同一事件一分钟内重复开口次数，应为 0。
6. TTS 首字节时间，判断是否值得建设预生成音频缓存。

建议目标：

```text
手机发现 P50 ≤ 5 秒
手机发现 P95 ≤ 10 秒
同事件重复提醒率 < 2%
明显误提醒率 < 5%
视觉请求并发数始终 ≤ 1
```

## 8. 后续路线

只有当 5 秒 Vision 版本验证了用户确实喜欢严格监管，再投入本地 CV：

1. 浏览器端每 0.5～1 秒做人脸存在、头部姿态或手机目标检测。
2. 本地检测持续达到阈值时才触发 Vision 确认。
3. 保留 20～60 秒低频 Vision 作为上下文观察。
4. 增加角色级快反音频缓存。
5. 用会话记忆生成“今天第三次了”等第二句话，但不阻塞首句。

成熟形态为：本地检测负责盯梢，Vision 负责确认，状态机负责节流，LLM 负责人设和上下文。

## 9. 本轮代码改动

- `frontend/js/focus-companion.js`
  - 视觉间隔改为 5 秒。
  - 第一次观察提前到摄像头启动约 1 秒后。
  - 固定间隔改为串行调度。
- `lib/companion-pipeline.js`
  - Vision 同时输出状态和置信度。
  - 删除正式观察链路中的二次状态分类调用。
  - 增加连续帧状态稳定器。
  - 增加关键事件与固定快反台词。
  - 在决策结果中返回 `rawState`、`confidence`、`stateChanged`、`event` 和 `speechMode`。
